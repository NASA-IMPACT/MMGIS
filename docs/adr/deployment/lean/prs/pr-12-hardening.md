# PR 12 — Hardening: DB-down boot, first-signup, superadmin, WebSocket heartbeat

**Depends on:** PR 1. **Blocks:** none (can land in parallel any time after PR 1).

> **Cross-PR seam (lean):** the superadmin seed and the first-signup gate added here only take effect on the lean deployment if **PR 11's admin task def injects them** — `SEED_SUPERADMIN_USERNAME`/`SEED_SUPERADMIN_PASSWORD` via `secrets[]` (Secrets Manager) and `DISABLE_FIRST_SIGNUP=true` via `environment[]`. Without those injections the seed never runs and the open first-signup page stays live on lean. This is a stated dependency on PR 11 so the seam isn't dropped (the code here is mode-agnostic; the env/secrets wiring lives in PR 11).

**Goal:** Land a small batch of production-readiness fixes that help every deployment — boot-time database retry, an automatic first-admin seed, a switch to turn off the open first-signup page, and a keep-alive heartbeat on the live-collaboration connection.

## In plain English

This is a grab-bag of fixes that make MMGIS sturdier in real-world hosting. None of them are specific to the lean deployment — they all help the full app too — they just happen to matter most once you run on cloud infrastructure with load balancers, auto-restarts, and public URLs.

First, when the app starts up it tries to talk to its database immediately and gives up if the database isn't answering yet. In the cloud, the database and the app often come back at slightly different times after a restart, so the app can crash simply because it was a few seconds early. We make startup wait and retry a handful of times before failing, so a normal restart is graceful instead of a crash loop.

Second, a brand-new install today shows an open "create the first admin account" page to whoever reaches it first. That's convenient for a laptop demo but a real security hole once the system is live on the internet — anyone could grab the first account. We add a way to seed that first admin automatically from secrets during a fresh deploy, and a switch to turn the open signup page off entirely.

Third, the real-time collaboration connection (the one that keeps multiple people's edits in sync) can be silently dropped after about a minute of quiet by load balancers, proxies, and mobile networks that close idle connections. We add a small "are you still there?" heartbeat from the server so the connection stays healthy and doesn't disappear mid-session.

## Implementation steps

1. **DB retry (`scripts/init-db.js`).** Wrap the connection attempt that actually determines success/failure (the `authenticate()` in `keepGoing()`, and/or an early `authenticate` before the `CREATE DATABASE` work) in a bounded retry: try, on connection-type failure wait a short delay and retry, up to a max attempt budget. After the budget is exhausted, reject so the existing top-level `.catch` exits non-zero and the orchestrator restarts the container. Read attempt count and delay from env with sane defaults.
   - **Retry predicate — don't rely on SQLSTATE alone.** `classifyPostgresError` (~L10) keys off the Postgres SQLSTATE `err.parent.code` and treats `08*`/`53300` as `connection_error`. But the **primary** DB-down-at-boot case — Postgres not yet accepting connections — surfaces as a Sequelize `SequelizeConnectionRefusedError` whose `err.parent.code === 'ECONNREFUSED'` is a **Node errno, not a SQLSTATE**, so `classifyPostgresError` falls through to `unexpected` and the loop would fail-fast — defeating the fix's primary purpose. The retry predicate must **also** catch connection-level failures: the Node errnos `ECONNREFUSED`/`ETIMEDOUT`/`ENOTFOUND` (on `err.parent.code` / `err.original.code`) **and** the Sequelize connection-error class names (`SequelizeConnectionRefusedError`/`SequelizeConnectionError`, plus `SequelizeHostNotFoundError`/`SequelizeConnectionTimedOutError`, detectable via `err.name` or `instanceof`). Retry when **either** the SQLSTATE class (`08*`/`53300`) **or** a connection-level signal matches; still fail fast on permission/config errors (e.g. `42501`). If extending `classifyPostgresError`, have it inspect these errno/class signals before the SQLSTATE branch so they're not mis-bucketed as `unexpected`.
2. **Superadmin seed (`scripts/init-db.js`).** After the database and extensions are ready, if both `SEED_SUPERADMIN_USERNAME` and `SEED_SUPERADMIN_PASSWORD` are set: ensure the `users` table exists (it is **not** created by init-db today — see notes below), check whether any users already exist, and if not, create one with permission `111`. Prefer importing the User model so the `beforeCreate` bcrypt hook hashes the password; if importing the model here is undesirable, hash with bcrypt and insert via raw SQL. Make it idempotent (no-op when a user already exists) and never log the password.
3. **Gate the route (`API/Backend/Users/routes/users.js`).** At the top of the `/first_signup` handler, if `process.env.DISABLE_FIRST_SIGNUP === "true"` respond `404` (or `next()` to the 404 handler) before doing anything. Leave all other behavior untouched.
4. **Client (`public/adminlogin.js` + `views/adminlogin.pug`).** Add `DISABLE_FIRST_SIGNUP` to the `res.render("adminlogin", ...)` context and expose it to the page. In `adminlogin.js`, when the flag is set, don't show/submit the create-account path; otherwise behave as today. As a minimum fallback, treat the gated 404 as a clear "signup is disabled" message rather than the generic "Server error."
5. **Heartbeat (`API/websocket.js`).** In `init`, after `websocket.wss = wss`, start a `setInterval` (period = `WEBSOCKET_PING_INTERVAL_MS` or 30000): for each `wss.clients`, if `client.isAlive === false` call `client.terminate()`, else set `client.isAlive = false` and `client.ping()`. In `wss.on("connection", (ws) => {...})`, set `ws.isAlive = true` and add `ws.on("pong", () => { ws.isAlive = true; })`. In `wss.on("close", ...)`, `clearInterval` the timer. No browser-side code is needed — the `WebSocket` API auto-answers pings.
6. **Docs (`sample.env`).** Add the new vars with one-line comments and their defaults / security notes (especially: leaving `DISABLE_FIRST_SIGNUP` unset keeps the open signup page, which is a risk once a system is publicly reachable).
7. *(Optional)* rename `webSocketPingInterval` → a reconnect-flavored name in the two client files for clarity. Pure rename.

## Verification

- **DB retry:** start init-db with Postgres down, then bring Postgres up mid-window — init-db connects on a later attempt and proceeds. With Postgres never coming up, it exits non-zero after the budget (clean failure the orchestrator can restart). A permission/config error still fails fast (not retried).
- **Superadmin seed:** fresh DB + `SEED_SUPERADMIN_USERNAME`/`SEED_SUPERADMIN_PASSWORD` set → a `111` admin exists and can log in; re-running init-db does not create a duplicate or error. With the vars unset, no seed runs.
- **first_signup gate:** with `DISABLE_FIRST_SIGNUP=true`, `POST /api/users/first_signup` returns 404; unset, it returns today's behavior. The admin login page does not show a broken "Server error." when the flag is set.
- **Heartbeat:** open the admin, leave Configure idle 10+ minutes behind an idle-closing proxy (or local nginx with `proxy_read_timeout 60s`) — the WS stays connected, no disconnect banner, Essence's reconnect logic does not fire. Killing a client without a clean close causes the server to `terminate()` it within ~2 ticks.

## Rollback

`git revert` the PR. All four changes are additive and default to today's behavior when the new env vars are unset (`DISABLE_FIRST_SIGNUP` unset = open signup as before; no `SEED_*` = no seed; retry budget only changes timing of an already-fatal condition; the heartbeat is transparent to clients), so reverting is low-risk for both modes.

## Implementation notes & gotchas

- **Seed ordering — the real risk.** `init-db.js` runs **before** the `users` table exists: table creation is `sequelize.sync()` in `scripts/server.js:589`, which runs *after* init-db in the `&&`-chained start scripts. So a seed placed in init-db must `CREATE TABLE IF NOT EXISTS` (or otherwise ensure the table) before inserting. Decide explicitly: (a) model-based seed (gets bcrypt hashing, but pulls the model + its `connection.js` dependency into init-db and still needs the table ensured), or (b) raw SQL seed with a manual bcrypt hash. Either way, ensure-table-first is required.
- **Client gating needs a Pug touch.** The clean window-flag approach touches `public/adminlogin.js`, `views/adminlogin.pug`, and the `res.render` call in `scripts/server.js:347`. The pure-404-handling fallback avoids the Pug/server edit if a smaller diff is preferred.
